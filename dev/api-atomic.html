JenaAtomicCalculator.Atomic.checkPropertySettings — Method

Atomic.checkPropertySettings(propertySettings) ... refuses a propertySettings list that carries TWO settings OF THE SAME TYPE. Nothing is returned; the offending case raises.

    **THE ARGUMENT IS DELIBERATELY UNTYPED**, and the first version of this guard got it wrong in exactly
    the way item 84 did: `[s1, s2]` written with two settings of ONE type has the concrete type
    `Vector{NuclearShielding.Settings}`, not `Array{Basics.AbstractPropertySettings,1}`, so a signature
    naming the abstract element type does not match the very case the guard exists for -- it raised a
    `MethodError` instead of the explanation. Anything that is not an array is passed over silently, since
    the keyword itself admits `Any`.

    **A `Computation` RUNS ONE COMPUTATION, FOR ONE PROPERTY OR ONE PROCESS, and higher complexity is not
    built on top of it** -- the maintainer's decision, 21-Oct-2026. A scan, a convergence study or a
    comparison of models is a SCRIPT: one `perform` does the structure, and the loop or the arithmetic sits
    around the terms it stored. The economics agree, measured on Th4+ [Rn] the same day: the
    self-consistent field costs 65.1 s and one shielding property on it 0.6 s, so the structure is 99 % of
    the work and six `Computation`s cost 5.8x what one field and a loop cost, for no physics.

    **IT RAISES RATHER THAN WARNS, AND THAT IS THE POINT.** Until this guard existed the duplicate was
    accepted and the result was LOST: every property branch of `Basics.perform` stores its outcome under a
    constant string key, so the second write replaced the first and `Base.merge` said nothing -- measured,
    two `NuclearShielding.Settings` differing only in `nVirtualMax` went in and ONE outcome came back, the
    second. There is no use for which that is the wanted behaviour, so a warning would leave a wrong number
    in circulation; this stops at construction, where the mistake is, rather than deep inside `perform`
    where only the symptom shows.

+ propertySettings  ::Array{Basics.AbstractPropertySettings,1}   ... the list as given to the Computation.

JenaAtomicCalculator.Atomic.warnAboutUnusedSettings — Method

Atomic.warnAboutUnusedSettings(comp::Atomic.Computation) ... warns about every AsfSettings field of the given computation that the path it will actually take can NEVER read, and whose value differs from the default. An Atomic.Computation carries FOUR such fields – asfSettings for the configs path, and initialAsfSettings / intermediateAsfSettings / finalAsfSettings for the initial/final path – deliberately, so that each multiplet may carry its own correlation model. Only the fields of the chosen path are consulted, and a value placed in one of the others is silently ignored: someone who sets eeInteractionCI = CoulombBreit(...) in asfSettings while giving initialConfigs gets a Coulomb-only CI with no indication why.

    THE COMPARISON AGAINST THE DEFAULT IS WHAT MAKES THIS USABLE. Every computation carries all four fields
    whether or not the user touched them, so a check that merely asked "is this path reading the field" would
    fire on every run and be ignored within a week. AsfSettings defines Base.:(==), so `!= AsfSettings()`
    separates "the user set this" from "untouched".

    IT IS A WARNING AND NEVER AN ERROR: one Computation may legitimately be built once and reused across paths.
    And it catches only a field that is NEVER consulted -- it cannot catch someone who fills initialAsfSettings
    where finalAsfSettings was meant, since both are read. Nothing is returned.

JenaAtomicCalculator.AdjustedLevels.buildParameterMatrices — Method

AdjustedLevels.buildParameterMatrices(sym::LevelSymmetry, basis::Basis, nm::Nuclear.Model, grid::Radial.Grid) ... the orthogonal route's generalization of AdjustedLevels.buildOneAndTwoBodyMatrices: instead of summing every two-body (Coulomb) contribution into ONE lumped matrix, each contribution is kept in the matrix belonging to its own (operator type, shell pair, rank) class, via AdjustedLevels.twoBodyParameterClass – Cowan's own F^k/G^k/R^k separation, which rank alone cannot give: two different shell pairs can share the same rank (a p-d pair's F^2 and G^2 both exist at k=2), and a correlation model with more than one active shell pair would otherwise have them fitted as if they were one physical quantity. A CLOSED subshell is never separately parametrized (Cowan's RCE fits the open shell(s) only, see this function's own comment on why), and a class whose matrix turns out to be a multiple of the identity on this block – the rank-0 monopole within one fixed- occupation open shell, most often – is folded into oneBody too, since no splitting could ever determine it. Even a single OPEN shell with l>=1 still separates into several classes, not one: its own relativistic j-splitting (e.g. 4f5/2 against 4f7/2) already gives distinct F^k, G^k and R^k integrals at a given rank, which a single rank-only bucket could not have told apart either. A (idxCsf, oneBody, parameterClasses, matrices) tuple is returned: idxCsf::Array{Int64,1} as in buildOneAndTwoBodyMatrices; oneBody::Array{Float64,2} the shared one-body matrix; parameterClasses ::Array{String,1} a label per discovered class; matrices::Array{Array{Float64,2},1} the matching upper-triangular two-body matrices, one per class, same convention as buildOneAndTwoBodyMatrices.

JenaAtomicCalculator.AdjustedLevels.fitOrthogonalParameters — Method

AdjustedLevels.fitOrthogonalParameters(sym::LevelSymmetry, basis::Basis, nm::Nuclear.Model, grid::Radial.Grid, targets::Array{Tuple{Int64,Float64},1}, source::String; determinacyThreshold::Float64=1.0e-6, maxIterations::Int64=20, tolerance::Float64=1.0e-6) ... the orthogonal (Uylings/Raassen-style) route: discovers the integral classes present in sym's block via buildParameterMatrices, fits one scaling parameter PER class against targets (same convention as fitScaleFactor's own targets), and reports the fit in terms of the ORTHOGONAL combinations the targets can actually determine. THE FIT IS A GAUSS-NEWTON ITERATION, not a single linearized step (that single-step version was tried first and MEASURED to leave a real, growing residual even in an idealised recovery test with exactly as many targets as free parameters – one linear step is only the leading-order correction to a genuinely nonlinear eigenvalue problem). At each iteration: diagonalize EXACTLY at the current parameters, build the sensitivity matrix J[target,class] = d(energy)/d(parameter) from the CURRENT eigenvectors (no extra diagonalization beyond the one already needed), take the MINIMUM-NORM correction via LinearAlgebra.svd (a direction the targets cannot determine is left untouched rather than amplifying noise), and re-center there for the next round. Iteration stops when the rms stops improving by more than tolerance, or after maxIterations – AND THE BEST ITERATE SEEN is what is returned, never just the last one: an undamped Gauss-Newton step is not guaranteed to improve the fit (measured directly: without this guard, one real case got WORSE after iterating, 175 to 323 cm^-1), so every candidate point is compared against the best found so far. MEASURED RANGE OF VALIDITY: on an idealised recovery test (synthetic targets generated from this route's own model, so a perfect fit exists in principle), this converges to the true parameters for corrections up to roughly 30% per class; beyond that the iteration can stall in a poorly-conditioned region well short of the solution (a slow, near-linear crawl, not an oscillation) rather than diverging outright. A correction this large is exactly the sign that the underlying ab initio calculation needs more correlation (more configurations), not a better fit – see this module's own docstring. value on each returned OrthogonalParameter is the TOTAL accumulated shift along that direction, and determinacy is read at the CONVERGED point, not the starting one – so a mode whose shift is reported but whose determinacy is still near zero signals the fit has not actually converged along it.     `V_HF phi_a = sum_b [ <b|b> phi_a - <b|phi_a> phi_b ]` to first order gives two exchange pieces with
    DIFFERENT pairings of the four subshells:

        E1 = -sum_b <chi_b|1/r12|phi_a> phi_b      pairs (t_a, b)   and (t_b, a)

    the 6j, and the two terms use the same one with `j_b` and `j_tb` swapped in the bottom row:

        E1:  (-1)^(j_tb + j_b + L + Lp) * 6j{ j_ta  j_a  L ;  j_tb  j_b   Lp }

RandomPhase.gmres(applyA::Function, b::Array{Float64,1}, maxIterations::Int64, tolerance::Float64) ... solves A x = b for a linear operator available only through its action applyA, by the standard Arnoldi/GMRES construction: build an orthonormal Krylov basis of b, A b, A^2 b, ..., and pick the combination minimising the residual over it.

    **WHY A KRYLOV SOLVER HERE AND NOT A MATRIX FACTORISATION.** The coupled system's operator is
    (I - M) on the concatenated channel sources, and M is never formed: assembling it in the B-spline
    basis would need one `RadialIntegrals.Yk_ab` sweep per column, which is O(N^2) per column and so
    hours of work for a case the map itself sweeps in seconds. GMRES needs only the action, and one
    action is one `RandomPhase.sourceMap` call. It is also indifferent to the spectral radius -- which
    is the whole point, since that radius is about 2.7 here and no fixed-point iteration can converge.

    This is unrelated to the Krylov/Lanczos CI eigensolver that was measured and DECLINED in Aug-2026:
    that was an EIGENVALUE problem for CI matrices, rejected because diagonalisation was a small share of
    wall time, and it proposed a new package dependency. This is a LINEAR SYSTEM whose iteration provably
    cannot converge, and it uses nothing beyond `LinearAlgebra`.

    A tuple (x, iterations, relativeResidual) is returned. The residual is the true GMRES residual
    ||b - A x|| / ||b||, so a caller can tell a converged solve from an exhausted one.

RandomPhase.receivingCoefficient(L::Int64, aSub::Subshell, tSub::Subshell) ... the one-electron angular factor the rank-L induced potential carries where it ACTS, i.e. at the active end of the channel aSub -> tSub, namely AngularMomentum.CL_reduced_me(aSub, L, tSub) / sqrt(2*j_a+1), or 0.0 where the triangular and parity selection rules forbid the channel. It is the counterpart of RandomPhase.angularCoefficient, which is the factor the induced DENSITY carries at the other end, and they are deliberately two functions because they are two different reductions of the same algebra.

    **WHY IT IS NOT `angularCoefficient`, AND HOW THAT WAS DECIDED -- 18-Oct-2026, priority item 75.** The induced
    potential and the EXTERNAL drive are both ordinary one-body potentials, acting on the same electron, in the same
    Dalgarno-Lewis equation; and a one-body potential has ONE matrix element, so the same radial function v(r) must
    produce the same source vector down either path. `DalgarnoLewis.solve` reduces its drive with
    `InteractionStrength.eMultipole`, which is CL_reduced_me(a, L, t)/sqrt(2j_a+1) times the bare radial integral --
    source first, and DIVIDED. Pushing v(r) = r down both paths on the nine E1 channels of Ne, the induced path as
    it stood returned -sqrt(2j_a+1)*CL(t,L,a)/CL(a,L,t) times the drive instead of 1.0, i.e. sqrt(2j_a+1) in
    magnitude with a channel-dependent sign, reproducible to 2.0e-15.

    alpha = (2/3)(2j_a+1) eMultipole(1, phi_a, chi), which reproduces 4.49972686 on this grid. So the drive's

With settings.couplingEnabled == true, the electrons are iterated together, each one's source gaining the DIRECT induced-potential contribution of every OTHER active electron's CURRENT chi (RandomPhase.inducedPotentialZr + RandomPhase.inducedSourceVector), until the induced potential's relative change falls below settings.accuracy or settings.maxIterations is reached – see the module's own docstring for what this coupled path has, and has not yet, been checked against. What blocks the wiring now is ONE angular convention shared by the induced direct term, the reduced exchange coefficient and the frozen operator – a derivation, not code – so the verified exchange lines in this file stay deliberately unwired; the module's own docstring states the measurement that leaves it open. A direct-only induced field over-screens, so a number from this function is a direct-only result in a strongly-coupled regime and NOT a validated screening correction. RandomPhase.sourceMap(multipole::EmMultipole, gauge::EmGauge, omega::Float64, activeOrbitals::Dict{Subshell,Orbital}, channels::Array{Tuple{Subshell,Subshell},1}, sources::Array{Float64,1}, potential::Radial.Potential, primitives::Bsplines.Primitives, dlSettings::DalgarnoLewis.Settings; occupiedOrbitals::Union{Nothing,Dict{Subshell,Orbital}}=nothing, occupations::Union{Nothing,Dict{Subshell,Float64}}=nothing, staticDrive::Bool=false) ... one application of the coupled map: given the induced source of EVERY channel, concatenated into a single vector, solve each channel's Dalgarno-Lewis equation and rebuild every channel's source from the resulting chi's. This is exactly one sweep of the fixed-point iteration, isolated so that it can serve as the matrix-vector product of a linear solver as well.

    **THE MAP IS AFFINE, AND THAT IS WHAT MAKES THE DIRECT SOLVE POSSIBLE.** Writing it as
    F(s) = b + M s, the drive b is simply F(0) -- the sources rebuilt from the UNCOUPLED chi's -- and the
    action of the linear part follows as M s = F(s) - b, with no matrix ever formed. The fixed point is
    the solution of (I - M) s = b, which exists whenever (I - M) is invertible, whether or not the
    spectral radius of M is below one.
    **`staticDrive` IS PASSED STRAIGHT THROUGH TO `DalgarnoLewis.solve`, and at omega = 0 it is not
    optional** -- the dynamic kernel is identically zero there, so every channel would be driven by
    nothing. `RandomPhase.solve` raises rather than let that happen; this function is the lower level and
    trusts its caller.
    A newSources::Array{Float64,1} of the same length is returned, together with the chis it passed
    through, as a tuple (newSources, chis).
