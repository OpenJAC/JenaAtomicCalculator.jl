JenaAtomicCalculator.Atomic.warnAboutUnusedSettings — Method

Atomic.warnAboutUnusedSettings(comp::Atomic.Computation) ... warns about every AsfSettings field of the given computation that the path it will actually take can NEVER read, and whose value differs from the default. An Atomic.Computation carries FOUR such fields – asfSettings for the configs path, and initialAsfSettings / intermediateAsfSettings / finalAsfSettings for the initial/final path – deliberately, so that each multiplet may carry its own correlation model. Only the fields of the chosen path are consulted, and a value placed in one of the others is silently ignored: someone who sets eeInteractionCI = CoulombBreit(...) in asfSettings while giving initialConfigs gets a Coulomb-only CI with no indication why.

    THE COMPARISON AGAINST THE DEFAULT IS WHAT MAKES THIS USABLE. Every computation carries all four fields
    whether or not the user touched them, so a check that merely asked "is this path reading the field" would
    fire on every run and be ignored within a week. AsfSettings defines Base.:(==), so `!= AsfSettings()`
    separates "the user set this" from "untouched".

    IT IS A WARNING AND NEVER AN ERROR: one Computation may legitimately be built once and reused across paths.
    And it catches only a field that is NEVER consulted -- it cannot catch someone who fills initialAsfSettings
    where finalAsfSettings was meant, since both are read. Nothing is returned.

struct AdjustedLevels.OrthogonalParameter ... one ORTHOGONAL combination of RadialParameters – a direction in parameter space, found from the measured targets themselves (see AdjustedLevels.fitOrthogonalParameters's own docstring for how), not stored or universal. value is the fitted SHIFT along this direction, away from the uniform, unadjusted (every RadialParameter = 1) starting point – NOT an absolute scale like ScalingParameter.value, since a direction is only meaningful as a combination of DEVIATIONS.

JenaAtomicCalculator.AdjustedLevels.fitOrthogonalParameters — Method

AdjustedLevels.fitOrthogonalParameters(sym::LevelSymmetry, basis::Basis, nm::Nuclear.Model, grid::Radial.Grid, targets::Array{Tuple{Int64,Float64},1}, source::String; determinacyThreshold::Float64=1.0e-6, maxIterations::Int64=20, tolerance::Float64=1.0e-6) ... the orthogonal (Uylings/Raassen-style) route: discovers the integral classes present in sym's block via buildParameterMatrices, fits one scaling parameter PER class against targets (same convention as fitScaleFactor's own targets), and reports the fit in terms of the ORTHOGONAL combinations the targets can actually determine. THE FIT IS A GAUSS-NEWTON ITERATION, not a single linearized step (that single-step version was tried first and MEASURED to leave a real, growing residual even in an idealised recovery test with exactly as many targets as free parameters – one linear step is only the leading-order correction to a genuinely nonlinear eigenvalue problem). At each iteration: diagonalize EXACTLY at the current parameters, build the sensitivity matrix J[target,class] = d(energy)/d(parameter) from the CURRENT eigenvectors (no extra diagonalization beyond the one already needed), take the MINIMUM-NORM correction via LinearAlgebra.svd (a direction the targets cannot determine is left untouched rather than amplifying noise), and re-center there for the next round. Iteration stops when the rms stops improving by more than tolerance, or after maxIterations – AND THE BEST ITERATE SEEN is what is returned, never just the last one: an undamped Gauss-Newton step is not guaranteed to improve the fit (measured directly: without this guard, one real case got WORSE after iterating, 175 to 323 cm^-1), so every candidate point is compared against the best found so far. MEASURED RANGE OF VALIDITY: on an idealised recovery test (synthetic targets generated from this route's own model, so a perfect fit exists in principle), this converges to the true parameters for corrections up to roughly 30% per class; beyond that the iteration can stall in a poorly-conditioned region well short of the solution (a slow, near-linear crawl, not an oscillation) rather than diverging outright. A correction this large is exactly the sign that the underlying ab initio calculation needs more correlation (more configurations), not a better fit – see this module's own docstring. value on each returned OrthogonalParameter is the TOTAL accumulated shift along that direction, and determinacy is read at the CONVERGED point, not the starting one – so a mode whose shift is reported but whose determinacy is still near zero signals the fit has not actually converged along it. THE ITERATION IS WARM-STARTED from the single-factor (uniform) optimum over these same matrices, not from all-ones: "every rank equal" is itself a point inside this route's own parameter space, so this route's rms can never be worse than fitScaleFactor's on the same targets – it WAS, measured, before this warm start was added, since a plain Gauss-Newton iteration can fail to reach even that nested point within maxIterations when starting far from it (confirmed on a real case: Pr IV 4f^2, J=2, where the orthogonal route returned a worse rms than the single-factor route on identical targets – mathematically impossible for the true optimum of a strictly richer, nested model). A fm::AdjustedLevels.FittedMultipletOrthogonal is returned.

Perturbed orbitals: the Dalgarno-Lewis equation

JenaAtomicCalculator.DalgarnoLewis.PerturbedOrbital — Type

struct DalgarnoLewis.PerturbedOrbital ... defines a type for the solution chi of a single Dalgarno-Lewis equation: the response of one electron, driven by one multipole operator from one source orbital at one energy, to a perturbation of frequency omega. UNLIKE an ordinary Radial.Orbital, this is not normalized to 1 – its magnitude is fixed by the source term's own strength, which is the physically meaningful quantity a caller reads off directly (e.g. by forming <final| O' |chi>, an ordinary one-body matrix element, with no further sum needed) – and it is not an eigenstate of anything, so "energy" here names the TARGET energy the equation was solved at, not a property chi itself possesses.

+ subshell       ::Subshell          ... the relativistic kappa-channel chi was solved in.
+ sourceSubshell ::Subshell          ... the subshell of the orbital that drove this equation.
+ multipole      ::EmMultipole       ... the multipole rank Mp of the operator O^(Mp).
+ gauge          ::EmGauge           ... the gauge the operator was evaluated in.
+ omega          ::Float64           ... the perturbing frequency; the equation was solved at the target
                                          energy sourceEnergy + omega (emission) or sourceEnergy - omega
                                          (absorption), per the sign convention of the caller's source term.
+ targetEnergy   ::Float64           ... the energy (H_eff - targetEnergy) was shifted by before solving.
+ P              ::Array{Float64,1}  ... large and ..
+ Q              ::Array{Float64,1}  ... small component of chi, on the standard grid, truncated at its
                                          own last significant point exactly as an ordinary Orbital is.
+ residual        ::Float64           ... the norm of (matrixA - targetEnergy*matrixB)*c - source, in the
                                          SAME units as the source vector itself -- a measured quantity
                                          confirming the linear solve actually satisfied the equation to
                                          the precision claimed, not a bare pass/fail. A caller that wants
                                          to trust chi should check this is small relative to norm(source),
                                          not merely that the solve returned without error.

JenaAtomicCalculator.DalgarnoLewis.amplitude — Method

DalgarnoLewis.amplitude(multipole::EmMultipole, finalOrbital::Orbital, chi::DalgarnoLewis.PerturbedOrbital, grid::Radial.Grid; omega::Union{Nothing,Float64}=nothing) ... computes <finalOrbital || O^(multipole) || chi>, i.e. the ordinary one-body matrix element a caller forms from a solved PerturbedOrbital, using chi's OWN gauge (chi.gauge) throughout – Coulomb/Magnetic via InteractionStrength.MabEmission directly, Babushkin via DalgarnoLewis.amplitudeKernel (fixed 11-Oct-2026; see that function's own docstring for why it, not MabEmission directly, is the right one here). The FREQUENCY this operator itself carries defaults to chi.omega (the equation's own omega, right for the single-operator case this function was first written for – e.g. a polarizability-type <i|O(omega)|chi(omega)>, where the probe and the perturbation share one frequency) – but a SECOND, genuinely two-photon-shaped use needs the OTHER photon's frequency here instead: in <final|O2(omega2)|chi1(omega1)>, the omega carried by O2 is omega2, which need not equal chi1.omega = omega1 at all except through the shared constraint omega1 + omega2 = Ei - Ef. The omega keyword exists for exactly that case; passing it explicitly changes NOTHING for any existing caller, since every one of them already relies on the default. A value::ComplexF64 is returned.

JenaAtomicCalculator.DalgarnoLewis.amplitudeKernel — Method

DalgarnoLewis.amplitudeKernel(multipole::EmMultipole, gauge::EmGauge, omega::Float64, a::Orbital, b::Orbital, grid::Radial.Grid) ... computes the same one-body multipole amplitude as InteractionStrength.MabEmission, EXCEPT that the Babushkin (length) branch's eps = a.energy <= b.energy ? 1 : -1 orientation correction is always taken as eps = +1, never read off a or b's .energy field. THIS IS THE FUNCTION DalgarnoLewis.solve AND DalgarnoLewis.amplitude USE FOR THE BABUSHKIN GAUGE – fixed 11-Oct-2026, after being wrongly marked insufficient earlier the same day; read this before changing it again.

    THE FORMULA ITSELF WAS NEVER WRONG. Grant (1974, J. Phys. B 7 1458), kept in
    `apps/papers/1974.jpb-grant-gauge-invariance.pdf`, derives the electric-multipole radial matrix
    element for an ARBITRARY gauge parameter G_L as M_e(G_L) = M_e(0) + G_L*M_longitudinal (his eq 4.10),
    a PURE LINEAR-ALGEBRA IDENTITY with no eigenstate assumption anywhere -- G_L is just a number. Setting
    G_L = sqrt((L+1)/L) (the Babushkin/length choice; his eq 6.9 confirms it reduces to the ordinary
    dipole LENGTH form at L=1) and expanding ALGEBRAICALLY (verified here by hand, term by term) gives
    EXACTLY `GrantJL(L) + (kapa-kapb)/(L+1)*GrantILplus(L+1) + GrantILminus(L+1)` -- i.e. THIS function,
    with its constant +1. No comparison of a and b's energies enters that derivation at any point.

    WHAT eps IS ACTUALLY FOR. Separately, Grant's Theorem A' shows the `GrantILplus`+`GrantILminus` piece
    VANISHES when a and b are BOTH genuine eigenstates of the SAME Hamiltonian (via the continuity
    equation) -- confirmed directly, 11-Oct-2026: for 1s/2p_1/2 at their own on-shell frequency the
    combination is ~1e-11 relative to GrantJL once box-truncation noise is accounted for, against ~1e-5
    in an earlier, looser check. On that near-cancellation, `MabEmission`'s `eps` exists to fix the
    OVERALL SIGN between two genuine, comparably-bound orbitals in the typical caller's convention
    (PhotoEmission and everywhere else in JAC) -- it is a convenience for THAT calling pattern, not a
    piece of Grant's general formula, and this function correctly leaves it out.

    WHY THE EARLIER "~12.9x TOO SMALL" VERDICT WAS WRONG, NOT THE FORMULA. The validation used to reject
    this function compared it against an explicit sum over the complete eigenbasis in which EACH TERM
    used `InteractionStrength.MabEmission`'s own ENERGY-DEPENDENT eps (varying from term to term, since a
    complete 1819-state basis spans states both above and below the two fixed endpoints) -- while this
    function, used consistently by `solve`'s source-vector step and by `amplitude`'s extraction step,
    computes the UNIFORM-sign version throughout. That is two different quantities, not one compared
    against itself. Rebuilt so BOTH sides use this SAME uniform function for every term: ratio 1.000000
    to 6 figures, checked at two different omega (0.3 and 0.15 a.u.) on H 2s -> 2p_1/2 -> 1s.

    THE ROLE-BASED CONVENTION THIS RELIES ON. `solve` and `amplitude` always call this function with `a`
    the EARLIER/DRIVING orbital in the Dalgarno-Lewis chain (the real source orbital in `solve`, chi
    itself in `amplitude`) and `b` the LATER/TARGET one (a synthetic primitive in `solve`, the final
    orbital in `amplitude`) -- NEVER swapped. A constant eps works BECAUSE that role assignment never
    swaps, not because +1 is the universally correct sign for an arbitrary (a,b) pair; this function is
    not a general-purpose replacement for `InteractionStrength.MabEmission` outside that calling pattern.
    The Coulomb/velocity and Magnetic branches carry no eps ambiguity at all (nothing in their formulas
    depends on it) and are passed through to `InteractionStrength.MabEmission` unchanged.
    A value::ComplexF64 is returned.

JenaAtomicCalculator.DalgarnoLewis.solve — Method

DalgarnoLewis.solve(multipole::EmMultipole, gauge::EmGauge, omega::Float64, targetSubshell::Subshell, sourceOrbital::Orbital, potential::Radial.Potential, primitives::Bsplines.Primitives; settings::DalgarnoLewis.Settings=DalgarnoLewis.Settings(), extraSource::Union{Nothing,Array{Float64,1}}=nothing, staticDrive::Bool=false) ... solves (Heff - targetEnergy) |chi> = O^(multipole, gauge) |sourceOrbital> for chi, in the kappa-channel of targetSubshell, where Heff is the one-body Dirac Hamiltonian for potential on the SAME B-spline primitives sourceOrbital was (or could have been) generated from, and targetEnergy = sourceOrbital.energy + omega. Reuses Bsplines.setupLocalMatrix for the Hamiltonian matrix exactly as Bsplines.generateOrbitals does – the only difference from an ordinary bound- or continuum-orbital generation is that this matrix is SOLVED against a source, not diagonalized.         Sum_nu <final|O2(omega2)|nu><nu|O1(omega1)|initial> / (E_initial - omega1 - E_nu)
      + Sum_nu <final|O1(omega1)|nu><nu|O2(omega2)|initial> / (E_initial - omega2 - E_nu)

    with the sum over nu COMPLETE (every state of this channel, not a truncated pseudostate set) by
    construction, exactly DalgarnoLewis's whole reason for existing. A caller still forms the physical
    amplitude by summing this over every allowed intermediate symmetry (targetSubshell), weighting each
    by its own Wigner-6j recoupling factor and multipole exchange phase -- that part is system-specific
    (it depends on Ji, Jf and the multipole ranks) and stays with the caller, exactly as
    `MultiPhotonTransition.computeReducedAmplitudeEmission` leaves it to ITS OWN caller.

    THE SIGN TRICK, recorded here because it is not obvious and cost real effort to get right (11-Oct-2026).
    `DalgarnoLewis.solve` can only be driven at a POSITIVE omega (`InteractionStrength.MabEmission`'s
    radial integrals raise a domain error for a negative one), but the first denominator above needs chi
    solved at targetEnergy = E_initial - omega1, i.e. at omega = -omega1 relative to initialOrbital. The
    fix is NOT to negate omega: it is to solve FROM finalOrbital instead, at omega2 = (E_initial-omega1) -
    E_final (POSITIVE, since omega1 + omega2 = E_initial - E_final by energy conservation), and then use

    directly, ratio exactly -1.000000 between a 1s-2p and a 2p-1s Coulomb-gauge matrix element -- to show
    the two resulting double sums are identical. VALIDATED (11-Oct-2026): for H 2s -> 1s this function's
    result, fed through the K=0 Wigner-6j/exchange-phase assembly, reproduces an INDEPENDENT explicit sum
    over the complete eigenbasis of the identical matrix to 7 significant figures (ratio 1.000000) in
    BOTH gauges, and the K=1 channel it leaves to the caller comes out at a 1.5e-11 share of K=0 --
    matching, to the digit, the share already measured by the sum-over-states code this is meant to
    replace. See example-As.jl branch (c) for the full H 2s -> 1s application and its result.

    GAUGE INVARIANCE, CHECKED DIRECTLY AND STRONGER THAN EXPECTED (11-Oct-2026). Calling this function
    with gauge = Basics.Coulomb and gauge = Basics.Babushkin, same omega1/omega2, agrees to 8 significant
    figures -- at every omega1 sampled across the full physical range (0, E_initial-E_final), not only at

    leg (one `DalgarnoLewis.amplitude` call alone, not the full two-time-ordering combination this
    function forms) shows NO such agreement (ratio -2.47, not close to 1) -- gauge invariance belongs to

JenaAtomicCalculator.RandomPhase.angularCoefficient — Method

RandomPhase.angularCoefficient(L::Int64, tSub::Subshell, aSub::Subshell) ... the one-electron angular factor the rank-L induced interaction carries on the channel aSub -> tSub, namely AngularMomentum.CL_reduced_me(tSub, L, aSub), or 0.0 where the triangular and parity selection rules forbid the channel. It exists as a named function, rather than inline, because the convention is the thing most easily got wrong here and Rule 18 asks for it to be visible.

    **WHICH CONVENTION, AND HOW IT WAS FIXED -- 14-Oct-2026.** `DalgarnoLewis.solve` builds its EXTERNAL
    source from `DalgarnoLewis.amplitudeKernel`, i.e. from a REDUCED one-electron matrix element on the
    channel aSub -> tSub. An induced source added to that same equation must therefore be reduced the
    same way, which is exactly one factor of `CL_reduced_me` per end and no division by sqrt(2j+1)
    anywhere. The argument ORDER matters and is not free: `CL_reduced_me(tSub, L, aSub)` and
    `CL_reduced_me(aSub, L, tSub)` differ by (-1)^(j_t - j_a), so they have OPPOSITE signs for
    2s_1/2 <-> 2p_3/2 and the same sign for 2s_1/2 <-> 2p_1/2. The order used here is the one
    `InteractionStrength.XL_Coulomb(L, a::Subshell, b, c::Subshell, d, primitives)` uses for the
    corresponding two-electron strength -- target (row) first, source (column) second -- so that this
    module's radial route and JAC's own already-validated angular factor agree term by term.

    **THE `(-1)^L` IS NOT APPLIED HERE.** `XL_Coulomb` carries it once for the whole two-electron
    product, and this function is called at BOTH ends -- once where the induced density is formed and
    once where it acts -- so applying it here would square it away. `RandomPhase.solve` applies it once,
    and says so at the line that does.
    A coefficient::Float64 is returned, which is 0.0 for a channel the selection rules forbid.

JenaAtomicCalculator.RandomPhase.gmres — Method

RandomPhase.gmres(applyA::Function, b::Array{Float64,1}, maxIterations::Int64, tolerance::Float64) ... solves A x = b for a linear operator available only through its action applyA, by the standard Arnoldi/GMRES construction: build an orthonormal Krylov basis of b, A b, A^2 b, ..., and pick the combination minimising the residual over it.

    **WHY A KRYLOV SOLVER HERE AND NOT A MATRIX FACTORISATION.** The coupled system's operator is
    (I - M) on the concatenated channel sources, and M is never formed: assembling it in the B-spline
    basis would need one `RadialIntegrals.Yk_ab` sweep per column, which is O(N^2) per column and so
    hours of work for a case the map itself sweeps in seconds. GMRES needs only the action, and one
    action is one `RandomPhase.sourceMap` call. It is also indifferent to the spectral radius -- which
    is the whole point, since that radius is about 2.7 here and no fixed-point iteration can converge.

    This is unrelated to the Krylov/Lanczos CI eigensolver that was measured and DECLINED in Aug-2026:
    that was an EIGENVALUE problem for CI matrices, rejected because diagonalisation was a small share of
    wall time, and it proposed a new package dependency. This is a LINEAR SYSTEM whose iteration provably
    cannot converge, and it uses nothing beyond `LinearAlgebra`.

    A tuple (x, iterations, relativeResidual) is returned. The residual is the true GMRES residual
    ||b - A x|| / ||b||, so a caller can tell a converged solve from an exhausted one.

JenaAtomicCalculator.RandomPhase.inducedPotentialZr — Method

RandomPhase.inducedPotentialZr(multipole::EmMultipole, activeOrbitals::Dict{Subshell,Orbital}, chis::Dict{Tuple{Subshell,Subshell},DalgarnoLewis.PerturbedOrbital}, excludeSubshell::Subshell, grid::Radial.Grid; occupiedOrbitals::Union{Nothing,Dict{Subshell,Orbital}}=nothing, occupations::Union{Nothing,Dict{Subshell,Float64}}=nothing) ... builds the DIRECT (Hartree, "ring") induced potential ONE electron of excludeSubshell feels from every OTHER active electron's CURRENT chi – its (N-1) PARTNERS IN ITS OWN SUBSHELL INCLUDED, whenever occupations is given – at the multipole's own rank L, in the SAME "Zr" (= -rV(r)) convention Radial.Potential and Bsplines.computeVlocal use throughout JAC – so that the minus sign below is the ordinary nuclear-potential-style sign, not a new convention. The induced density itself is 2[PbPchi_b + QbQchi_b] – the psichi + chipsi symmetrization for a real response – which is exact only at omega = 0, since at finite omega the two terms are the two time orderings and are different functions.

    **THE WEIGHT IS sqrt(2j_b+1) TIMES THE CHANNEL'S REDUCED MATRIX ELEMENT, AND THE sqrt IS NOT A TYPO.**
    Until 14-Oct-2026 each electron b was weighted by the full (2j_b+1), treating it statistically as a
    filled shell, with no angular factor at all -- which made the coupled iteration diverge (see
    `RandomPhase.solve`). The weight is fixed, without any literature, by the L = 0 HARTREE LIMIT:

      * at L = 0 with t_b = b the induced potential must be the ordinary first-order Hartree potential,
        2*(2j_b+1)*Y_0[rho]/r, which is what the old code had and what is not in dispute;
      * the source this potential feeds is `DalgarnoLewis.solve`'s, which is REDUCED -- it comes from
        `DalgarnoLewis.amplitudeKernel`, a reduced one-electron matrix element -- so the induced term must
        be reduced to match, one factor of `CL_reduced_me` per end (see `RandomPhase.angularCoefficient`);
      * and `AngularMomentum.CL_reduced_me(b, 0, b) = sqrt(2j_b+1)` EXACTLY, checked for s, p, d and f.

    Equating the two therefore gives weight * sqrt(2j_b+1) = 2*(2j_b+1), i.e. a weight of
    2*sqrt(2j_b+1): the occupation splits in half, one sqrt(2j_b+1) staying here and the other being
    carried by the reduced matrix element's own normalisation. This is precisely the sqrt(2j+1) Rule 18
    is about, and it is written out because the two quantities it sits between -- an ordinary potential
    and a reduced source -- are otherwise denoted alike.

    **AND THE ANGULAR FACTOR CHANGES THE PHYSICS, NOT ONLY THE SCALE.** `CL_reduced_me(b, L, t_b)` carries
    a SIGN, and for the two spin-orbit partners of a subshell those signs are OPPOSITE: for L = 1,
    CL(2p_1/2, 1, 2s_1/2) = -0.816 against CL(2p_3/2, 1, 2s_1/2) = +1.155. So the partners partially
    cancel in the induced field, where the old weighting added them with one sign and with weights 2 and
    4. That cancellation is physical and is a large part of why the uncorrected term was far too strong.

    **THE RADIAL PART IS VERIFIED AGAINST JAC'S OWN, TO TEN DIGITS.** `InteractionStrength.XL_Coulomb`
    builds the corresponding two-electron strength from `RadialIntegrals.SlaterRkComponent`, so the two
    can be compared entry by entry if the source orbital is chosen to BE a single B-spline, which makes
    its coefficient vector a unit vector. Done on the Ne case for three spline pairs, this route and
    JAC's agree to every digit printed -- ratio 1.000000, values -7.3537752978e-03 against
    -7.3537752978e-03 -- SIGN INCLUDED. So the radial machinery and the "Zr" sign convention here are the
    ones JAC uses elsewhere, and the angular factor was the only thing this module lacked.
    A VindZr::Array{Float64,1} of length grid.NoPoints is returned.

JenaAtomicCalculator.RandomPhase.sourceMap — Method

RandomPhase.sourceMap(multipole::EmMultipole, gauge::EmGauge, omega::Float64, activeOrbitals::Dict{Subshell,Orbital}, channels::Array{Tuple{Subshell,Subshell},1}, sources::Array{Float64,1}, potential::Radial.Potential, primitives::Bsplines.Primitives, dlSettings::DalgarnoLewis.Settings; occupiedOrbitals::Union{Nothing,Dict{Subshell,Orbital}}=nothing, occupations::Union{Nothing,Dict{Subshell,Float64}}=nothing) ... one application of the coupled map: given the induced source of EVERY channel, concatenated into a single vector, solve each channel's Dalgarno-Lewis equation and rebuild every channel's source from the resulting chi's. This is exactly one sweep of the fixed-point iteration, isolated so that it can serve as the matrix-vector product of a linear solver as well.

    **THE MAP IS AFFINE, AND THAT IS WHAT MAKES THE DIRECT SOLVE POSSIBLE.** Writing it as
    F(s) = b + M s, the drive b is simply F(0) -- the sources rebuilt from the UNCOUPLED chi's -- and the
    action of the linear part follows as M s = F(s) - b, with no matrix ever formed. The fixed point is
    the solution of (I - M) s = b, which exists whenever (I - M) is invertible, whether or not the
    spectral radius of M is below one.
    A newSources::Array{Float64,1} of the same length is returned, together with the chis it passed
    through, as a tuple (newSources, chis).
