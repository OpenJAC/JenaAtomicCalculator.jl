Validation against another code

Almost every check a code applies to itself is self-referential. JAC's test suite compares against reference files that JAC itself produced; the cancellation factor and the gauge ratio that flag a doubtful transition are formed from the very amplitudes they judge; and the Last successful date on an example records one person's reading of JAC's own output. None of that can detect an error that JAC makes consistently.

This page is the exception: a standing comparison against values that do not come from JAC. It is regenerated mechanically, so nothing on it is typed in by hand.

How a row must be read

The rows are grouped by tier, because the tier decides what a difference means. A relative difference of $10^{-7}$ is a defect in one tier and entirely expected in another, and a table that mixes them says nothing at all.

tierthe reference isa difference means
0a closed-form expression — the Dirac energy of a one-electron ion in a point nucleusthe discretization of one of the two sides; it bounds how sharply anything else can be compared
1another code solving the same equations with the same configuration state functionsa defect in one of the two codes
2another code using a different methodinformative, never decisive: the two calculations are not the same calculation

Within a tier the rows are ordered by the quantity compared, since that is the question a reader arrives with — can I trust JAC's transition rates? — rather than by which partner supplied the reference. The partner is therefore a column: where two codes cover one quantity, their rows belong side by side.

What is pinned, and why

A comparison is only as sharp as the agreement between the two problems being solved, so everything that could differ is fixed rather than left to each code's defaults:

  • a point nucleus, because two finite-nucleus models are never identical and the difference would be read as a difference between the codes;
  • the Coulomb interaction only, with no Breit term and no QED correction — these are the terms a closed-form Dirac energy does not contain, and the terms whose implementations may legitimately differ;
  • a single reference configuration, so that the list of configuration state functions is one function in both codes and no correlation model stands between them. This is what makes a tier-1 difference a defect, and it is possible only with a partner that uses the same formalism.

The radial grids are deliberately not made identical, and that is not an oversight. A finite-difference integrator carries a value at every radius, while JAC expands each orbital in a fixed set of B-splines; the same four grid parameters therefore do not describe the same discretization for the two codes, and a grid well suited to one can starve the other. Each code is run on a grid adequate for itself, and the comparison rests on the Hamiltonian and the function list being identical.

The same rows are written to validation-rows.csv, one line per comparison, carrying each row's model, its grid, its tolerance and the partner's pinned commit under field names that are expected to stay stable. That file is there so that another project's harness can read these comparisons, add a column of its own and check them, without needing anything from us.

What this does not establish

Every row here tests whether JAC implements a given set of equations correctly. None of them can say whether the equations were the right ones for a particular atom: the choice of correlation model, of mean field and of basis remains a physical judgement, and agreement with another code is no substitute for it. A clean table is necessary, and it is a long way from sufficient.
